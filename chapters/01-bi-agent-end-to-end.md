# A data agent end to end

By the end of this chapter, you can build the shop's warehouse, have a recorded model write SQL for a business question, run that SQL and catch the wrong number it returns, answer the same question from one defined metric, and score both approaches on five golden questions. It is the whole result of this book in rough form: every later chapter makes one part of it solid.

The request this book answers usually arrives as one sentence: let people ask the data. Someone in finance wants net revenue by region for last month without waiting for a dashboard, and someone hands you a language model. The obvious build gives the model the warehouse's schema and the question, runs the SQL it writes and shows the result. On a hand-picked question that build often works, which is enough to demo; on this book's five golden questions it gets {{out:score-five-golden:schema-only correct}} right. Its failures are the problem, because most of them don't look like failures. A query that fails to run is an error someone sees. A query that runs and returns a number a few percent too high goes into a slide.

This chapter builds the obvious version first, runs it, and shows exactly where its number goes wrong. Then it builds the smallest version of the alternative the book recommends: an agent that can't see tables at all, only a defined metric, and that says so when the metric doesn't cover a question. Both are scored on the same five questions with checked answers, the habit the rest of the book depends on.

You need Python {{version:python}} and SQL, and nothing else: no GPU, no cloud account and no API key. Every example runs offline on DuckDB {{version:duckdb}}, against data the book generates, and every model reply it uses was recorded once from an open model and is replayed from a file.

## Meet the shop and its warehouse {#meet-the-shop}

An agent that answers questions from a warehouse can only be as right as the warehouse's definitions let it be. Real warehouses hold more than tables: they hold decisions about what counts as an order, which currency a total is in and which day a timestamp belongs to. Those decisions live in the marts, in the SQL that built them and in the heads of the people who wrote it. So to see where an agent goes wrong, you need a warehouse with those decisions in it, and the traps they create.

This book follows one case throughout: an online shop that sells outdoor and camping gear in three regions, EMEA, AMER and APAC, which we call the shop. It has no brand name and stands for no real business. Its data is generated by the book's own code, `lib/shop_data.py`, from one fixed seed, so every reader builds exactly the same rows. Orders run from {{out:load-the-warehouse:first order day}} to {{out:load-the-warehouse:last order day}}, and nothing in the data depends on the day you run an example.

The shop's warehouse, which every example queries, is a DuckDB database with two schemas, as an analytics engineer would build them. The `raw` schema holds what the source systems loaded: orders, order lines, refunds, customers, products, sessions, marketing spend and exchange rates. The `analytics` schema holds the marts built from them in SQL, such as `fct_orders`, one row per real order with its amounts in euros. `lib/warehouse.py` does the build. Its `connect()` generates the data, loads `raw`, runs the SQL that builds `analytics`, and returns a connection that can read but not write, with access to other files switched off.

The row counts are the quickest way to see them, so the example builds the warehouse and prints them.

[Example: load-the-warehouse](../examples/load-the-warehouse.py)

The counts already show three decisions, and the first is that the mart drops the shop's own test orders. `raw.orders` holds {{out:load-the-warehouse:raw.orders}} orders and `analytics.fct_orders` holds {{out:load-the-warehouse:analytics.fct_orders}}, so the {{out:load-the-warehouse:test orders in raw.orders}} test orders, placed from the shop's test accounts, never reach the mart. The customers shrink between `raw.customers` and `analytics.dim_customers` for another reason: some customers signed up twice, with emails that differ only in case, and test accounts are left out. The mart keeps the {{out:load-the-warehouse:cancelled orders in fct_orders}} cancelled orders, each with its status, because some questions are about cancellations.

Other decisions aren't visible in a count. EMEA prices include VAT and AMER and APAC prices don't, so gross and net revenue differ by region. Timestamps are stored in UTC, while the shop counts sales on each region's local business day. The fiscal year starts on February 1, and is named for the year it ends in. And `analytics.orders_legacy`, an older mart that old dashboards still read, has a column called `revenue` that holds a different number: gross, tax included, test orders kept. Nothing in the schema says which of these rules applies to which question.

**Working rule:** Build the agent against a warehouse that has your real traps in it: test rows, cancelled orders, several currencies, local business days, a fiscal calendar and at least one legacy table with a tempting name. Generate it from a seed when you can't share production data, so anyone can rebuild it. A clean demo schema hides exactly the failures you need to see.

## Ask a question, get SQL from a model {#ask-for-sql}

With the [shop's warehouse](#meet-the-shop) built, the obvious next step is to let a model query it. Schema-only text-to-SQL means the model is given the name and type of every column and the person's question, and nothing else, and writes the SQL. In our experience it is where many first builds start, because the schema is the one description of the warehouse that exists, and the database keeps it current. What it leaves out are the definitions, which the schema doesn't hold.

A book whose examples called a model would give a different answer on every run, and would need an API key. So every model reply in this book is recorded. A recording is a saved set of model replies with a manifest, made once by a script in the repository's `recordings/` folder and replayed by the examples. The model is Qwen3-4B-Instruct-2507, which Qwen releases under the Apache 2.0 licence. It has 4.0 billion parameters and answers without a separate thinking phase, so a reply is the answer alone ([Qwen's model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)). We run a 4-bit quantization of it, a file of about 2.5 GB pinned by its SHA-256 hash ([the file](https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF/tree/a06e946bb6b655725eafa393f4a9745d460374c9)), on four CPU threads with llama-cpp-python, so anyone can record it again without a GPU.

The sampling settings are the ones Qwen recommends for this model: temperature 0.7, top-p 0.8, top-k 20 and min-p 0 ([Qwen's model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)). The seed is reset before every call. Replies are capped at 384 tokens for SQL and 256 otherwise. That cap is our choice, to keep a recording run short on a CPU, where Qwen suggests 16,384. Each recording's `manifest.json` names the script, the model and its file hash, the prompt's hash, the sampling, the date and each call's time.

On the examples' side, `lib/model.py` provides `RecordedModel("schema-only-sql")`, which replays that recording. It looks each reply up by the SHA-256 of the exact messages sent. A prompt that differs by one character has no recording, and the replay stops with an error instead of returning a reply to some other prompt. The prompt itself is a constant in `lib/prompts.py`, `SCHEMA_ONLY_SQL`, shared by the recording script and the examples.

The question is one the finance team asks every month: "What was net revenue in each region in March 2026?" It is also `gq-002`, a golden question with a checked answer; the next section tests the answer against it. Before judging its number, read the SQL the model writes.

[Example: first-question-to-sql](../examples/first-question-to-sql.py)

The prompt lists all {{out:first-question-to-sql:tables in the prompt}} tables of both schemas as `CREATE TABLE` statements, {{out:first-question-to-sql:prompt tokens}} tokens with the instructions and the question. The line that matters here is the one for `analytics.fct_orders`. It has a `net_revenue_eur` column, an `order_date_local` column, a `region` and a `status`.

The SQL the model wrote is what many analysts would write first. It picks the mart over the raw tables and over `orders_legacy`. It sums `net_revenue_eur`, not gross. It filters on `order_date_local`, so each order lands on its region's business day instead of its UTC day. It groups by region and gives the column a sensible name. If you were reviewing this query in a pull request, you might approve it. The question is whether the number it returns is right, and nothing in this output can tell you.

**Working rule:** Treat schema-only text-to-SQL as the baseline to beat, not as the product. Run it once on your own warehouse and keep its replies, because it shows you which of your definitions the schema doesn't carry. Record every model reply your tests depend on, pinned to a model file, a prompt hash and fixed sampling, so a failure you find can be reproduced by someone else.

## Run the SQL and check the number {#check-the-first-number}

The model's query for March 2026 [looks right](#ask-for-sql), and it runs. A query that fails is caught when someone sees the error; one that runs and returns a plausible number is the failure that matters, because nothing marks it as wrong. The only way to know is to compare the result with an answer someone has checked.

A golden question is a question with its checked answer: the golden SQL, written against the owner's definition, the golden result that SQL returns, and the kind of answer expected. The golden SQL is checked by running it, which chapter 3 covers. The book keeps its golden questions in `examples/data/golden/questions.toml`, and `lib/golden.py` loads them. The golden SQL for `gq-002` follows the shop's definition of net revenue, which the finance team owns: revenue in euros after discounts and before tax, from real orders that weren't cancelled, on the order's local business day.

Put the model's query beside the golden one, region by region, with each region's cancelled orders alongside to check the gap against.

[Example: run-the-model-sql](../examples/run-the-model-sql.py)

The query overstates net revenue by exactly the cancelled orders it counts. For EMEA it reports {{out:run-the-model-sql:EMEA model}} euros against a golden {{out:run-the-model-sql:EMEA golden}}, and the gap, {{out:run-the-model-sql:EMEA cancelled orders}}, is the net revenue of EMEA's cancelled orders that month. AMER and APAC follow the same pattern. Across the three regions, the model's total is {{out:run-the-model-sql:overstated by}} above the golden total.

The query wasn't careless. The schema shows a `status` column, but nothing in it says cancelled orders don't count toward revenue. That rule lives in the finance team's definition, which a model reading column names can't see. A larger model might guess the rule more often, but a guess is the wrong mechanism: the next question may depend on a rule nobody would guess, such as which day a refund belongs to.

Notice what the check compares: the rows, not the SQL text, and here the rows don't match. `results_match()` in `lib/golden.py`, the rule every score in this book uses, rejects them, which the example checks.

**Working rule:** Never accept an agent's number because its SQL looks right. Check it against a golden result before anyone relies on it, and when the two differ, find the rows that explain the difference before you change anything. Expect the difference to be a definition, such as which orders count, more often than a syntax mistake.

## Answer from one defined metric {#answer-from-a-metric}

Counting cancelled orders [broke the first number](#check-the-first-number), because the rule that excludes them isn't in the schema. The fix this book recommends is to stop asking the model for SQL over tables, and to give it defined metrics instead. A metric is a business measure written down once, by the people who own it: a name, a description a person can check, one aggregate over one mart, the rule for which rows count, and the dimensions it may be grouped and filtered by. The model's job shrinks to choosing a metric and its arguments. Code that you wrote and tested turns that choice into SQL.

This chapter has one metric, `net_revenue`, in `lib/metrics.py`. Its rule for which rows count is the finance team's: `status <> 'cancelled'` on `analytics.fct_orders`. Its dimensions are `region`, `channel`, `fiscal_year`, `fiscal_quarter`, `calendar_year` and `calendar_month`, each mapped to one SQL expression. A metric request names the metric, the dimensions to group by and one value per filtered dimension, and `compile_request()` turns it into SQL. Dimension names come only from that list, and filter values are passed as query parameters, never pasted into the SQL text.

The model reaches the metric through tools. A tool is a function the model may ask the code to run, by replying with a JSON object that names it and gives its arguments. This agent has two, in `lib/tools.py`. `query_metric` computes a metric for a request. `cannot_answer` declines, with a one-sentence reason, when no metric covers the question. The loop that connects them is the book's own, `run_agent()` in `lib/agent.py`. It sends the messages, reads one tool call from the reply, runs the tool and stops when the tool returns an answer, after at most three model calls. The prompt, `METRIC_TOOLS` in `lib/prompts.py`, lists the metric's description and each dimension's meaning, including when the fiscal year starts. It lists no tables.

The recording `metric-tool-runs` holds the same model's replies to the metric prompt, recorded the way `schema-only-sql` was. Here is `gq-002` again, through the metric.

[Example: one-metric-answer](../examples/one-metric-answer.py)

The model asked for `net_revenue`, grouped by `region` and filtered to calendar month 3 of calendar year 2026. The SQL the code compiled from that request applies the cancelled-orders rule, joins the date dimension on the local business day and passes the month and year as parameters. Each region matches its golden result.

The answer also carries its provenance: the metric that produced it, the filters, the role it was computed for, and how fresh the data is. The `data as of` line is when the newest row in `fct_orders` was loaded, read from its `_loaded_at` column. A person can see the definition and the currency of a number without reading SQL.

One metric is a long way from a semantic layer. It can't join through entities, it has one grain and it holds one definition. Chapter 5 replaces it with a semantic layer that does those things. The shape stays, though: the model chooses a governed definition, and code writes the SQL.

**Working rule:** Route a question to a defined metric before you let a model write SQL. Give the model the metric's description and its dimensions, and let it return a request, which your code validates and compiles. Write SQL from a model only for questions no metric covers, and only behind guards.

## Score both on five golden questions {#score-five-questions}

One question answered [from the metric](#answer-from-a-metric) shows the approach can work. It doesn't show that it works more often than [schema-only SQL](#ask-for-sql). For that, score both on golden questions under the same comparison rule. A score on five questions is a smoke test, not a measurement, and it can't support a claim about this model, or about text-to-SQL in general. It still separates outcomes that one accuracy figure hides.

Each answer gets one of four outcomes. It is correct when the result matches the golden result, or when it declines a question that should be declined. It is wrong when it returns a different result, or returns any result for a question that should be declined. It is an error when the SQL doesn't run. It is declined when it says it can't answer a question that has an answer. A decline is not a wrong number, and a score that counts the two together hides the difference this book cares about most.

The comparison rule, `results_match()` in `lib/golden.py`, accepts an answer when it has as many rows as the golden result and its columns include every golden column's values. Columns are matched by their values, not their names, so column order doesn't matter, and neither do extra columns, such as a `fiscal_year` column beside the total. Row order doesn't matter unless the question says it does. Numbers must agree within 0.05 percent, or within half a cent. Chapter 3 discusses each of these choices.

The five golden questions cover the traps one at a time:

| ID | Question | Kind |
| --- | --- | --- |
| `gq-001` | Net revenue in fiscal year 2026 | answer |
| `gq-002` | Net revenue in each region in March 2026 | answer |
| `gq-003` | Net revenue by sales channel in calendar 2025 | answer |
| `gq-004` | Customers whose first order was in fiscal 2026 | answer |
| `gq-005` | Net revenue next quarter | decline |

Both approaches face all five, and the output has one row per question, showing where each one fails.

[Example: score-five-golden](../examples/score-five-golden.py)

Schema-only SQL gets {{out:score-five-golden:schema-only correct}} questions right, and the way it fails matters more than that count. It fails to run on {{out:score-five-golden:schema-only error}} questions: for `gq-001` and `gq-003` the model filtered `fct_orders` on `fiscal_year` and `calendar_year`, columns that exist only in `dim_date`. Those failures are visible, which makes them the cheap ones. Its wrong answers, on {{out:score-five-golden:schema-only wrong}} questions, are not. `gq-002` counts cancelled orders. `gq-004` counts customers whose first order fell in calendar 2026 instead of fiscal 2026. And `gq-005`, a forecast the warehouse can't make, gets a query over the quarter that contains today's date, which runs and returns a total instead of saying the question can't be answered.

The agent with one metric gets {{out:score-five-golden:metric correct}} questions right, including the decline for the forecast, and makes {{out:score-five-golden:metric wrong}} wrong answers. It declines `gq-004`, which the warehouse can answer but `net_revenue` can't, since it counts revenue, not customers. That decline is the cost of the approach, and it is the right cost. A person who hears "I can't answer that from the metrics I have" knows to ask someone, while a person who hears a wrong count doesn't.

Small as it is, the score does show one thing. On this warehouse, the failures came from definitions the schema doesn't hold, and moving the definitions into code removed them. Chapter 3 builds the golden set to 48 questions, with a held-out split, and every later chapter reports its numbers on it.

**Working rule:** Score every change on golden questions written from your own work, and report correct, wrong, error and declined separately. Include questions that should be declined from the start, or an agent that never declines will look perfect. Use a handful of questions as a smoke test while you build, and a larger set with a held-out split before you claim anything.

### Read the trace of one run {#read-one-trace}

A score says how often the agent was right. A trace says why, for one run. The trace is every step of one run, kept by `run_agent()`: each model reply, and each tool result sent back. Reading traces shows whether a correct outcome was correct for the right reason, and what a decline rested on.

The agent declined `gq-004` in the [five-question score](#score-five-questions), so this replay prints every step of that run.

[Example: print-one-trace](../examples/print-one-trace.py)

The decline was the right call, but its reason is false. Declining is right because `net_revenue` can't count customers. The reason says the data has no information about the number of customers who placed their first order in a fiscal year, while `analytics.dim_customers` has a `first_order_on` column. The run ended with a call to `cannot_answer`, a reason instead of a result, after {{out:print-one-trace:model calls}} model call in all. The model saw only the metric's description and dimensions, so it claimed things about data it couldn't see. A reader would conclude the warehouse can't answer the question, which isn't true.

**Working rule:** Read traces, not only scores, and read the declines first. Check that each decline's reason is about what the agent was given, such as "no metric counts customers", and not a claim about data it never saw. Treat a decline with a false reason as a defect, even when the score counts it as declined.

## What goes wrong in production {#end-to-end-in-production}

The rough agent built here works on five questions. These are how the design fails once people depend on it, and how you'd notice each.

**A plausible number goes into a decision.** Schema-only SQL that runs returns a number with no warning attached, as [`gq-002` showed](#check-the-first-number) with a total {{out:run-the-model-sql:overstated by}} too high. Nobody notices until someone compares it with the finance team's report, often weeks later. The early warning is scoring on golden questions before release and after every change, and showing provenance with each answer, so a reader sees which definition was used.

**Definitions drift away from the metric.** The metric's description says cancelled orders don't count, and its SQL enforces that. When the finance team changes a rule, such as excluding a marketplace's fees, the description, the SQL and the golden SQL all need the same change. If one is missed, the agent's answers and the golden results move apart, and the score drops. That drop is the alarm, so keep the golden questions in the same repository as the metric definitions, and review changes to both together.

**The agent declines for a reason that isn't true.** The [trace of `gq-004`](#read-one-trace) declined correctly but claimed the data has no first-order dates. A person who believes that reason stops asking. You notice by reading declines in traces, and by keeping golden questions that the warehouse can answer but the metrics can't, so a false reason shows up as a decline on a question you know is answerable.

**A model reply changes without anyone noticing.** If an example called a model live, a new model version or a changed prompt would change every downstream number silently. The replay in `lib/model.py` looks replies up by the hash of the exact messages, so a changed prompt stops with `MissingRecording`. Record again on purpose, and treat a new model version like a library release: record, score and compare.

**The model file's chat template isn't the publisher's.** The quantized file this book records with embeds a chat template that differs from the one Qwen publishes for this model ([Qwen's template](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507/blob/cdbee75f17c01a7cc42f958dc650907174af0554/tokenizer_config.json)). The embedded one adds an empty thinking block to an assistant turn that ends the conversation, which Qwen's own template doesn't do. Our recording runtime, `recordings/local_model.py`, renders every prompt with Qwen's template at a pinned revision, checked by hash, and each manifest records whether the embedded template matched. Comparing the two before the first recording catches it, not a run of odd replies afterward.

**Stale data answers confidently.** The metric's answer said when the newest row in `fct_orders` was loaded. A mart whose load stopped would still answer, from old data, unless something checks that date against what the question needs. Show the date with every answer at least, and decline when it's too old for the question.

**The model's SQL runs with no checks.** In this chapter, `run_sql()` in `lib/tools.py` executes whatever the model wrote. Here the warehouse connection is read-only and can't open other files, which limits the damage to reading. A production warehouse connection usually has more rights than that. Never give a model's SQL a connection that can write: connect it read-only to a database that holds only what the asker's role may read ([chapter 7](#views-per-role)), and add guards in front of it as defence in depth.

**Working rule:** Before anyone outside your team uses the agent, make every failure above visible: score on golden questions in CI, show provenance and data freshness with each answer, review declines in traces, replay recorded replies by message hash, and run model-written SQL only on a read-only connection. Start with golden scoring, because it is the only one of these checks that catches a plausible wrong number.

## Decisions this chapter made {#end-to-end-decisions}

- **The book's running case is a shop we generate.** The shop's warehouse is generated from one seed, with the traps a real warehouse has, so every reader gets the same rows and nothing depends on private data.
- **The warehouse is read-only.** `warehouse.connect()` returns a connection that can't write and can't open other files, so even unchecked SQL can only read.
- **The baseline is recorded for real.** Schema-only SQL's replies come from the pinned model above, with Qwen's recommended sampling and a seed reset before every call.
- **Every model reply is recorded and replayed by message hash.** A changed prompt fails loudly instead of reusing an old reply.
- **Metrics come before SQL.** The model chooses a defined metric and its arguments; code validates the request and writes the SQL.
- **Declining is an answer.** The agent has a `cannot_answer` tool, and scores count declined separately from wrong.
- **One comparison scores everything:** rows are compared, not SQL text, by the same rule every time: the same rows, every golden column present, any order, a small tolerance.
- **The loop is ours, not a framework's.** It is a few dozen lines in `lib/agent.py` that a library release can't change. A framework's development can stop: vanna, an open-source text-to-SQL framework, was archived by its maintainers on 29 March 2026 ([repository](https://github.com/vanna-ai/vanna)).
